# Код-рев'ю

## Main.java

1. - Файл починається з порожнього рядка.
2. - Заголовний коментар записано як звичайний блоковий `/* */`, а не Javadoc `/** */`, тож ні IDE, ні утиліта `javadoc` його не обробляють.
3. - У `@author george` вказано ім'я системного користувача замість справжнього імені автора.
4. - `@project Default (Template) Project` - лишилася шаблонна назва проєкту замість `Triangle`.
5. - `@class ${NAME}` - змінну шаблону так і не замінено на реальне значення.
6. - Рядок `@version 1.0.0` закінчується зайвим пробілом (trailing whitespace).
7. - `@since 05/09/2026 - 20.16` - з дати не зрозуміло, де день, а де місяць, а час записано через крапку, що нестандартно.
8. - У коді лишилися коментарі `//TIP ...` із шаблону IntelliJ; до проєкту вони не мають стосунку і тільки заважають читати.
9. - Метод `void main()` оголошено без класу (unnamed class / instance main). Без preview-режиму такий запис працює лише починаючи з JDK 25, до того ж із коду не видно, якому класу він належить.
10. - Не вказано `package`; клас із пакета за замовчуванням не можна імпортувати в інших пакетах.
11. - `String.format("Hello and welcome!")` викликається без аргументів, тому нічого не форматує - вистачить звичайного рядкового літерала.
12. - Повідомлення "Hello and welcome!" - залишок демо-коду з шаблону, який не стосується задачі.
13. - Цикл, що виводить `i = 1..5`, - ще один шаблонний приклад, ніяк не пов'язаний із трикутниками.
14. - Число `5` використано напряму, без іменованої константи.
15. - `Main` ніяк не працює з `Triangle`, тож програма фактично нічого не показує.
16. - Користувач не може задати сторони трикутника: їх не зчитують ні з консолі, ні з аргументів командного рядка.
17. - Помилки не обробляються: некоректне введення чи `NumberFormatException` ніде не перехоплюються.

## Triangle.java

18. - Файл теж починається з порожнього рядка.
19. - Не оголошено `package`.
20. - Клас не має Javadoc-опису, тому незрозуміло, для чого він, у яких одиницях задаються сторони і які обмеження мають виконуватися.
21. - `equals` позначено як `final`, а сам клас - ні. Це непослідовно: слід або зробити `final` увесь клас, або прибрати `final` з `equals`.
22. - Імена полів `a`, `b`, `c` нічого не пояснюють; зрозуміліше було б `sideA`, `sideB`, `sideC`.
23. - Поля не `final`, тобто об'єкт можна змінювати, хоча ці поля використовуються в `hashCode()`. Якщо змінити сторону вже після того, як трикутник потрапив у `HashSet` чи `HashMap`, знайти його там більше не вдасться.
24. - Назви `takeA/putA` не відповідають угоді JavaBeans (`getA/setA`), через що багато інструментів і фреймворків не розпізнають ці методи.
25. - Сеттери приймають будь-яке значення без перевірки, зокрема від'ємні числа, нуль, `NaN` і `Infinity`.
26. - Шість однотипних методів доступу роздувають клас; для незмінного об'єкта-значення краще підходить `record`.
27. - Конструктор не перевіряє, що сторони більші за нуль.
28. - Конструктор не перевіряє нерівність трикутника (`a + b > c` тощо), тому можна створити трикутник, якого не існує, наприклад зі сторонами `1, 1, 10`.
29. - Значення `NaN` та `Infinity` конструктор теж пропускає.
30. - Конструктор без параметрів створює «трикутник» зі сторонами 0, 0, 0, тобто об'єкт у невалідному стані.
31. - Конструктори розміщено після методів доступу, хоча за конвенцією спершу йдуть поля, потім конструктори, а вже потім методи.
32. - Тут відступ у 3 пробіли, тоді як у решті файлу - 4; це суперечить і Google Style, і Sun Checks.
33. - `perim` - скорочена назва; правильніше `perimeter` або `getPerimeter`.
34. - З назви `area` не видно, що метод щось обчислює; зазвичай пишуть `getArea` або `calculateArea`.
35. - В одному виразі `perim()` викликається чотири рази - це повторні обчислення та дублювання коду.
36. - Число `0.5` трапляється чотири рази як магічне; його варто винести в локальну змінну `semiPerimeter`.
37. - Уся формула записана в один рядок довгим ланцюжком множень і погано читається; її краще розбити на кілька кроків.
38. - Навколо операторів немає пробілів (`0.5*perim()-a`), що порушує стиль оформлення коду.
39. - Якщо трикутник не існує, `Math.sqrt` отримує від'ємне число й мовчки повертає `NaN` замість того, щоб повідомити про помилку.
40. - Для дуже витягнутих («голкоподібних») трикутників формула Герона дає великі похибки; надійніше застосувати варіант Кахана з попереднім сортуванням сторін.
41. - У `public  boolean  equilateral(){` стоять подвійні пробіли, а перед `{` пробілу немає.
42. - Метод, що повертає `boolean`, слід назвати `isEquilateral()`.
43. - Конструкція `if (...) { return true; } else return false;` надлишкова - достатньо `return a == b && b == c;`.
44. - `else return false;` записано без фігурних дужок і в тому ж рядку, що й `}`, а це суперечить Google Style.
45. - Перед закривальною дужкою методу є зайвий порожній рядок.
46. - Значення `double` порівнюються через `==`, що ненадійно через похибки округлення; до того ж в `equals` для цього використано `Double.compare`, тобто в одному класі два різні підходи.
47. - Визначається лише рівносторонній трикутник, а рівнобедрений, прямокутний і різносторонній - ні, тож функціональність неповна.
48. - Згідно з `equals` трикутники `(3, 4, 5)` і `(5, 4, 3)` різні, хоча насправді вони рівні (конгруентні). Порядок сторін не мав би впливати на результат, а якщо так задумано, це треба явно описати в документації.
49. - На початку `equals` бракує швидкої перевірки `this == o`.
50. - Рядок із трьома порівняннями довший за 100 символів, що перевищує ліміт Google Style.
51. - `toString` збирає рядок конкатенацією; читабельніше використати `String.format`, а в `record` цей метод генерується автоматично.
